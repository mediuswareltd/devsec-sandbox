About this demo

This page simulates a MongoDB-backed login that is vulnerable to NoSQL injection. No real database is used — the vulnerability is replicated in JavaScript so you can see exactly what happens inside the query.

In a real vulnerable application, the server accepts a JSON body and passes it directly to db.collection.findOne(). When the attacker sends {"$gt":""} as the password, MongoDB treats it as a query operator rather than a literal value — and authentication is bypassed.

Open nosql-fixed.html to see the safe version.

The vulnerable code

// On the server (Node.js + Express + mongoose) — VULNERABLE:
app.post('/login', async (req, res) => {
  // req.body is parsed from JSON by bodyParser.json()
  // The attacker sends: { "username": "admin", "password": { "$gt": "" } }

  const user = await User.findOne({
    username: req.body.username,
    password: req.body.password  // VULNERABILITY: could be an object!
  });

  // MongoDB sees: { username: "admin", password: { $gt: "" } }
  // $gt: "" means "password field value > empty string" → matches ANY password!
  if (user) {
    return res.json({ token: generateToken(user) });  // attacker gets in!
  }
});

Why does this work?

MongoDB query operators like $gt (greater than), $ne (not equal), $regex, and $where are designed to be used in query documents. When user-supplied JSON reaches findOne() without type-checking, an attacker can inject these operators as query conditions.

{ password: { "$gt": "" } } tells MongoDB: "find a document where the password field is greater than an empty string" — which is true for every stored password, so authentication is bypassed.
